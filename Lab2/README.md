Отчёт по лабораторной работе №2

Паттерны проектирования: Наблюдатель, Прокси, Стратегия. Перегрузка операторов

1. Цель работыРазработать и реализовать систему управления орбитальной станцией с командным центром, космическим окружением и внешними объектами/аномалиями.
Реализовать паттерны Наблюдатель, Прокси и Стратегия, а также перегрузку операторов для взаимодействия объектов.Язык реализации: C++.

2. Текстовое описание архитектурыСистема состоит из следующих основных частей:CommandCenter (Командный центр)
Хранит модули станции
Ведёт учёт ресурсов: энергия, кислород, уровень безопасности
Реализует интерфейс IObserver и получает уведомления от модулей
Работает с текущим космическим окружением через прокси
Поддерживает перегрузку оператора + для добавления ресурсов
Иерархия окружений (Environment)
Абстрактный класс Environment с методами applyEffect, getName, getEnergyModifier, getDamageModifier
Конкретные окружения:
EarthOrbit — слабое влияние
DeepSpace — повышенный расход энергии и повреждения
AsteroidField — снижение прочности и блокировка исследовательских модулей

Паттерн Прокси
Класс EnvironmentProxy реализует тот же интерфейс, что и Environment
Добавляет дополнительные проверки (например, блокировку модулей) и логирование перед передачей управления реальному окружению
Паттерн Стратегия
Интерфейс IInteractionStrategy
Конкретные стратегии: CrewModuleStrategy, EnergyModuleStrategy, ResearchModuleStrategy, ReactorModuleStrategy
Разные типы модулей по-разному реагируют на одно и то же окружение
Внешние объекты / аномалии
Абстрактный класс ExternalObject
Конкретные классы:
SolarStorm — радиационные повреждения
MeteorShower — физические повреждения
CargoContainer — добавление ресурсов
SpaceAnomaly — случайная модификация характеристик

Паттерн Наблюдатель
IObservable / IObserver
Модули уведомляют командный центр о событиях: Activated, Damaged, Destroyed, EnergyConsumed
Класс ModuleEvent хранит информацию о событии
Перегрузка операторов
Module - Damage — нанесение урона
Module * double — изменение эффективности
CommandCenter + ResourcePackage — пополнение ресурсов

3. Реализация паттерна «Наблюдатель»Модули наследуются от IObservable и хранят список наблюдателей.
При изменении состояния (повреждение, уничтожение, активация) модуль создаёт объект ModuleEvent и вызывает notify().CommandCenter реализует IObserver и в методе onModuleEvent реагирует на события:
при повреждении снижает уровень безопасности
при уничтожении удаляет модуль из списка

4. Реализация паттерна «Прокси»EnvironmentProxy хранит указатель на реальное окружение (std::shared_ptr<Environment>).
В методе applyEffect сначала выполняются дополнительные проверки (например, заблокирован ли модуль), затем управление передаётся реальному объекту окружения.
Также прокси добавляет информацию о себе в название окружения.

5. Реализация паттерна «Стратегия»Каждое окружение (особенно DeepSpace и AsteroidField) выбирает подходящую стратегию в зависимости от типа модуля и вызывает её метод apply().
Это позволяет одному и тому же событию по-разному влиять на жилые, энергетические и исследовательские модули без изменения кода самих модулей.

6. Перегрузка операторов
operator- уменьшает прочность модуля и автоматически отправляет уведомление наблюдателям
operator* изменяет эффективность модуля
operator+ добавляет ресурсы в командный центр
Все операторы учитывают состояние модуля (например, заблокированные модули не получают урон).

7. Результаты демонстрационных сценариевПрограмма успешно выполняет следующие сценарии:
Создание командного центра и добавление модулей разных типов
Установка окружения через EnvironmentProxy
Смена окружения на DeepSpace с применением стратегий
Воздействие SolarStorm и MeteorShower (повреждения + уведомления)
Получение ресурсов через CargoContainer
Случайный эффект SpaceAnomaly
Работа AsteroidField с блокировкой исследовательских модулей
Все уведомления Наблюдателя корректно отображаются, ресурсы и прочность изменяются правильно.

8. Выводы В ходе работы были реализованы три основных паттерна проектирования:
Наблюдатель — для реакции командного центра на изменения модулей
Прокси — для контроля доступа и дополнительного поведения при взаимодействии с окружением
Стратегия — для гибкого изменения влияния окружения в зависимости от типа модуля
Также успешно применена перегрузка операторов для удобного и выразительного взаимодействия объектов.

Архитектура получилась расширяемой: новые окружения, стратегии и внешние объекты можно добавлять без изменения существующего кода командного центра и модулей.
